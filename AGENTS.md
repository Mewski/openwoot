# openwoot: notes for coding agents

Keyboard firmware for Wooting hall-effect keyboards, written in Rust, with its own configuration protocol shared with a Rust host application.

**State: feature-complete; a daily keyboard on the Wooting 80HE.** On the owner's 80HE (TenZ edition): enumerates at 480 Mbit/s as stock does; types with stock-like actuation; LEDs and light bar show the factory profiles and react; the Mode key, Fn + 1 to 4 and Fn + F11/F12 brightness work; `openwoot version`, `openwoot status` and `openwoot flash` work over the configuration channel; the official Wootility returns it to stock. Host-tested: scanning and the analog model, keys incl. advanced keys, gamepad and XInput, storage, lighting, light bar and signals, profiles and editions, the configuration model, runtime commands, the stock identification responder and RGB SDK commands. Not yet checked on hardware: advanced keys, gamepad, XInput, host LED control, sensor readout, `GetKeyGeometry`, and `openwoot-gui` (every page rendered against the firmware's configuration handler running on the host, never against a keyboard). The Wooting 60HE+ has never run on hardware. Update this file whenever the layout, commands or rules change.

## Layout

| Path | Holds | May depend on |
| --- | --- | --- |
| `crates/openwoot/` | the firmware: `hid` (descriptor builder, typed reports), `xinput` (XInput report and interface), `usb` (the USB face over any `embassy_usb_driver::Driver`), `protocol` (configuration channel, stock responder, the `UpdateMode` trait the chip HAL's bootloader implements), `diagnostics` (relaxed atomic counters in `runtime::State`, the `Transfers` bus counters the chip HALs keep, the `Readout` behind `GetDiagnostics`), runtime, analog, scan, storage, lighting; it defines the traits it needs from hardware; `no_std`, no hardware access, tested on the host | `openwoot-protocol`, `openwoot-drivers`, `openwoot-image`, ecosystem crates |

| `crates/openwoot-image/` | the firmware image format: the image descriptor, its location, the image checks, the `memory.x` reader; `no_std`; used by boards, the CLI and `xtask` | ecosystem crates only |

| `crates/openwoot-gd32f4/`, `crates/openwoot-gd32f3/` | one HAL per microcontroller family on its PAC (`rt` only for `target_os = "none"`): `rcu`, `gpio` (typed `Pin`s and the runtime `Line`), `i2c`, `spi`, `scan` (the hall-sensor converter), `flash`, `time` (embassy-time driver), `interrupt` (`bind_interrupts!`, `Priority`; a reference to a binding is a binding too, so a board can take `&dyn Interrupts`), `executor` (`run`, `Spawners`: the thread executor and the key, device and lighting interrupt executors), `system` (reset, update-mode hand-over), `usb` (`usb::Driver`, `usb::negotiated_speed()`; the GD32F425 wraps `embassy-usb-synopsys-otg` with the ULPI PHY, the GD32F303 has a port of embassy-stm32's fsdev driver under `src/usb/`), `diagnostics::hardware()` (converter overruns, `i2c::transfers()`, `spi::transfers()`); private `basepri` (critical section), `dma` (the only code on DMA channels) and `register`; `system::Bootloader` implements `openwoot::protocol::UpdateMode`; `app_descriptor!`; the only hand-written crates with `unsafe` (`#![allow(unsafe_code, reason = ...)]`) | exactly one PAC (their own), `openwoot`, `openwoot-image`, ecosystem crates |

| `crates/openwoot-cli/` | host tool `openwoot` (`version`, `status`, `flash [--dry-run]`) over `openwoot-host`: the command line and its output; `indicatif` | `openwoot-protocol`, `openwoot-image`, `openwoot-host` |
| `crates/openwoot-gui/` | desktop configurator `openwoot-gui` (GPUI through `gpui-kit`), laid out and behaving like Wootility, measured against it (Wootility's wording and Nunito Sans font; icon rail with help menu, collapsible navigation panel, header with the profile switcher, undo/redo and save; keyboard fixed on top, page heading, cards): Quick Settings, My Profiles, Actuation Point, Rapid Trigger, Remap, Advanced Keys, Gamepad, RGB Settings, Light Indicator, Keyboard Settings, Switch Selector and Updates, the keyboard drawn from `GetKeyGeometry`; shared widgets: `keyboard` (keys with sweep selection, drag and drop, glyphs, markers, callouts), `dropdown` (Wootility's menus), `switch`, `slider`, `color_picker` (its pipette picks from the whole screen through `eye_dropper`: an `xcap` capture under an overlay with a magnifier on macOS and Windows, converted to sRGB with the display's profile and explaining a missing macOS screen-recording permission; the desktop portal's colour picker through `ashpd` elsewhere), `panel` (page frame, headings, cards, buttons, banners, dialogs); `history` (undo/redo through `Store::change`), `profile_parts` (whole-profile read and write); `assets/` holds the theme (`theme.json`, Wootility's palette) and the bundled font with its licence; one worker thread owns the `openwoot-host` connection (`device`), `store::Store` caches the keyboard and tracks unsaved changes | `openwoot-protocol`, `openwoot-host` |
| `boards/<board>/` | one board support crate per keyboard and its firmware binary in `boards/<board>/firmware/` (see Boards) | everything above except the host crate, the CLI and the GUI |
| `xtask/` | build helper: list boards, build images, checks, flashing via the CLI, PAC generation | `openwoot-image` |

Optional features (light bar, host signals, editions, ...) and alternative behaviours (noise recalibration methods, device-information storage) are modules with types in `crates/openwoot/`; a board selects them in its library. Shared crates have no Cargo features that depend on a board, and no shared code names a board or a family.

## Boards

- A board is a board support crate `boards/<board>/`, kebab-case, package name = directory name: a library with the board facts as typed constants (name, USB ids, update mode, protected flash areas, key matrix), `DESCRIPTOR`, the `Interrupts` its peripherals need (a trait over the HAL's `Binding`s), `pub struct Board` (the configured drivers and peripherals by board function, built by `Board::new(peripherals, &Irqs)`, which also opens the settings storage; it takes `irqs: &dyn Interrupts` and is `#[inline(never)]`, so it is not generic and is compiled in the board support crate), per-area modules with the board's data and the few functions that select it (`keys`, `lighting`, `profiles`, `scan`, `storage`), `configuration` (the shared state, the profile model, the `channel`, `profiles` and `lights` tasks, `hand_over`, which passes the configuration channel to thread mode, and `start`, which hands back the parts of every task), re-exports `hal` (its chip HAL) and `entry`; `memory.x` and `build.rs` as board support crates ship them.
- Its firmware is the package `openwoot-<board>` in `boards/<board>/firmware/` with the binary of the same name: the interrupt bindings (`hal::bind_interrupts!`), `app_descriptor!`, `main`, `start` (spawns every task on its executor) and the time-critical tasks (`scanning`, `device`, `reports`); its `build.rs` passes the linker arguments, the link map (`-Map`) among them.
- Speed and size are split by crate: everything is generic over the board's hardware, so a crate's `opt-level` applies to what it instantiates. The release profile builds at `opt-level = 2` (the stock firmware is built with GCC `-O2`; higher levels grow the code past the 60HE+'s zero-wait flash); each board support crate is listed with `opt-level = "z"` in the workspace `Cargo.toml`, so the configuration side (storage, profile model, configuration protocol, start-up) and the lighting task are compiled for size, while the firmware binary, the final crate of the link, instantiates the interrupt handlers and the key and USB tasks for speed. `xtask check` rejects an image in which an interrupt vector or a task of the key or device executor reaches code that a crate compiles for size (the crate of each function comes from the image's DWARF compile units); the lighting executor is size-compiled by design.
- `memory.x` is the single source of the image area, RAM and the zero-wait flash (`ZERO_WAIT`), and places the image descriptor (section `.app_descriptor`) on the first 64-byte boundary behind the vector table; `build.rs` reads it into the constants `IMAGE` and `RAM`.
- The image describes itself: the descriptor (`openwoot_image::Descriptor`) carries the board name, USB ids, update mode (product id, block size and `UpdateProtocol`), image area and RAM; the initial stack pointer must be the end of that RAM. There is no `board.json`; the CLI never lists boards, and `xtask` finds them under `boards/`.

## Real time

- Interrupt priorities: 0 the hall-sensor scan only (never masked), 1 the time driver and the LED and NOR bus interrupts (I2C0 event and error and its DMA channel, the NOR receive DMA channel), 2 USB, 3 the key executor (UART4 vector: `scanning`), 4 the device executor (UART3 vector: `device`, `reports`), 5 the lighting executor (USART2 vector: `lights`); thread mode runs only the configuration side (`channel`, `profiles`). Each executor pre-empts the ones below it: the key pass never waits behind USB, lighting or flash I/O, the USB device and reports never wait behind a frame or a settings write, and lighting, compiled for size on the lowest executor, keeps its 62.5 Hz render cadence. The scan does wait for lighting, by design and as in the stock main loop: no transfer to the LED driver may overlap a conversion (writes to the IS31FL3741 push the hall-sensor samples taken meanwhile up by tens of counts), so every one (a frame page with its page select, the wake and the shutdown write) waits in `runtime::LedWindow` for a gap, and between two scan cycles, after the key pass, the key task lets at most one transfer run and starts the next cycle when it ends, after `LedWindow::TRANSFER_LIMIT` (2 ms) at the latest. Only the driver's initialization runs outside a gap, with the driver shut down (it starts with a software reset): at start-up beside the calibration sweep, as stock's does, and after three failed steps behind a shutdown written in a gap. Critical sections raise BASEPRI to `0x10` and never mask the scan interrupt, and the scan interrupt takes none (`xtask check` rejects a BASEPRI write reachable from the scan vector, `ADC` or `ADC0_1`).
- TIMER4 belongs to the time driver; the vectors of UART4, UART3 and USART2 (the peripherals are unused) to the key, device and lighting executors. `hal::executor::run(start)` starts all four executors and hands `start` their `Spawners { thread, keys, device, lighting }`. The `device` task builds the USB device (`runtime::UsbParts::build`), passes the configuration channel to thread mode through `configuration::hand_over` (a static `Signal`) and spawns `reports` with the device executor's `SendSpawner` it was given; nothing uses `Spawner::for_current_executor`.
- The configuration side is synchronous: the profile model, the configurator and the settings store are plain functions, and flash I/O runs to completion through `embassy_futures::block_on`, only in thread mode, where every executor pre-empts it. State crosses between thread mode and the executors only through `keys::Shared` and `profile::Shared` (critical-section blocking mutexes held only to copy a value), atomics, `Signal`s and the host-control mailboxes. The profile model lies in a `RefCell` that only the two thread-mode tasks borrow, never across an await; a borrow that fails answers `StorageInaccessible`. No lock is held across flash I/O, and no interrupt executor ever waits on thread mode. The `lights` task owns the lighting engine (`&'static mut`, no async mutex).
- `memory.x` aligns `_stext` to 8 bytes behind the descriptor.
- The key executor runs the board's task named `scanning` and nothing else, the device executor `device` and `reports`, the lighting executor `lights`; `xtask check` finds their poll functions by these names and treats every interrupt executor as an interrupt context.
- All code (`.vector_table` and `.text`) lies in the zero-wait flash (`ZERO_WAIT` in `memory.x`: the first 512 KiB on the GD32F425, 256 KiB on the GD32F303; beyond it every fetch waits, and the 80HE's scan interrupt took 20 times as long and starved the thread-mode tasks), as the stock firmware's code does; constants may extend beyond it. The image is linked in the compiler's order, the same for `cargo build` and `xtask build`; nothing reorders it, and code that does not fit is made smaller. `xtask check` rejects an image whose code extends beyond `ZERO_WAIT`.
- No panic is reachable from an interrupt vector or a task of an interrupt executor (`xtask check`, call graph from the image's relocations; boards link with `--emit-relocs`, and an image with a call that has no relocation is rejected). The graph follows calls and the addresses taken in code and tables; it does not follow calls through pointers stored at run time (wakers, `dyn` objects registered at run time), and it leaves out the panic of an `async fn` resumed after completion. Every unnamed input section of the link map (anonymous constants, vtables) is a node of its own, so a reference is attributed to the exact object; `xtask build` copies the map to `build/<board>/openwoot-<board>.map`. A panic site of a pinned dependency that cannot fire goes into `xtask/src/check/panic_paths/reviewed.rs` with file, line, function, the contexts it is reached from (`reached_from`: `Origin::Interrupt`, `Origin::Task(Executor::..)`) and reason; panics in our code are fixed, never listed.
- A panic resets the microcontroller: each board's panic handler calls `hal::system::reset`. Faults and unclaimed vectors still end in the looping `cortex-m-rt` default handler.
- Statics (from the start of RAM to the end of the last static section) plus the stack bound of the call graph fit each board's RAM with 2048 bytes to spare. The stack bound is thread mode (start-up, or the thread executor plus its deepest task), plus the deepest task of each interrupt executor, plus every interrupt handler; `xtask check` prints it per board (`RAM N bytes static + N bytes stack (N thread, N keys, N device, N lighting, N interrupts)`) and rejects calls that form a cycle, since recursion has no bound. Start-up work with large values runs in its own `#[inline(never)]` function so its frame is gone before the tasks run; `main` only starts the executors.

## Rules

- Pure Rust: no C, assembly files, Python, shell scripts or make. Prefer maintained ecosystem crates over own code; justify each new dependency (maintenance, `no_std`, `unsafe`, licence compatible with MIT). Exact version pins live in `[workspace.dependencies]`, added when a crate first uses them (cargo warns about unused entries).
- `unsafe` only in the chip HAL crates (and the generated PACs), each with a `// SAFETY:` comment that gives its reason on its first line and sits on the `unsafe` line or directly above it (attributes may stand between); a note above no `unsafe` code is rejected.
- No panics on the scan or USB path; no heap. `xtask check` proves the first for the interrupt handlers (USB included) and every task of an interrupt executor (`scanning`, `device`, `reports`, `lights`); the thread-mode tasks (`channel`, `profiles`) rest on review.
- The microcontroller flash below the image base holds the factory bootloader, and the pages above the image end hold the serial number and device information. Code must never erase or program either; `memory.x` keeps the linker out of them, and each board checks its image area against them with a constant assertion in `src/lib.rs` and a test.
- The USB face (ids, interfaces, HID reports, the analog report read by the Wooting Analog SDK) stays close to stock; deviations are listed in `docs/protocol.md`.
- Nothing is flashed to a keyboard and nothing is pushed without the owner's go-ahead.
- No backwards-compatibility machinery (endpoint versions, pinned keys, record migrations) before the first tagged release; change types and paths freely.
- Commits: one line, conventional (`feat(keys): ...`, `fix(usb): ...`, `docs: ...`).

## Naming

- Rust API Guidelines naming: RFC 430 casing; acronyms are one word (`UsbIds`, `Hid`, not `USB`); constructors `new`/`with_*`, conversions `from_*`; `as_`/`to_`/`into_` by cost; getters without `get_`; iterators `iter`/`iter_mut`/`into_iter`; no `-rs`/`-rust` in crate names; Cargo features without `use-`/`with-`.
- Names say what a thing is in the domain (`actuation_point`, not `ap`, `val`, `data`, `tmp`, `info`, `mgr`, `util`, `helper`, `common`); no modules named `utils`, `misc`, `helpers`, `common` or `types` (`xtask check` rejects them).
- No stuttering: `keys::Index`, not `keys::KeyIndex`.
- Enforced by clippy (`pedantic` plus `module_name_repetitions`, `min_ident_chars`, `renamed_function_params`, `pub_underscore_fields`, `same_name_method`).

## Messages and strings

One voice everywhere a person reads text: errors, CLI output, help, `xtask` output, logs, panic messages, docs examples.

- Errors (`Display` of error types, `anyhow` context, `bail!`): lowercase first word, no trailing period, say what failed and with what (`could not read \`image.hex\``, `reset vector 0x0800_0000 lies outside the image`). Context is added at each layer with `with_context`, and printed as one chain with `{error:#}` (`openwoot: could not read \`image.hex\`: No such file or directory`). Never `Error:`/`error:` prefixes inside messages and never `failed to`; prefer `could not <verb>`.
- Error enums derive their messages with `thiserror` `#[error("...")]`, same rules; variants name the condition (`ResetVectorOutsideImage`), not the check.
- Help text (clap `about`/`help`): sentence case, no trailing period, imperative (`Write a firmware image through the factory bootloader`).
- CLI output: results to stdout as aligned `label: value` lines (labels lowercase, padded to one width per command), progress and diagnostics to stderr; every program prefixes its own fatal error with its name (`openwoot: ...`, `xtask: ...`).
- Identifiers, paths, commands and values from input appear in backticks in messages (`` `wooting-80he` ``, `` `--dry-run` ``).
- Numbers: addresses and register values as lowercase hex with `0x` and `_` every four digits (`0x0800_8000`); USB ids as `31e3:1400`; sizes with their unit spelled out (`3 blocks of 256 bytes`, `768 bytes`); durations with units (`250 ms`).
- Names of products as their makers write them (`Wooting 80HE`, `Wooting 60HE+`, `GD32F425`); everything else lowercase in running text.
- All user-facing strings of one kind live next to the type they describe (error enums, one `show`/output function per binary), never scattered `println!` with ad-hoc formats.

## Code style

- Code documents itself: names, types and small functions carry the meaning. No comments, no doc comments and no commented-out code. The one exception is the `// SAFETY:` comment that every `unsafe` block or attribute requires.
- Lints are set once in the workspace `Cargo.toml` (`[workspace.lints]`, clippy pedantic plus denials of panics, `unwrap`, indexing, `todo!` and undocumented `unsafe`); every crate except the generated PACs has `[lints] workspace = true`. An `#[allow]` or `#[expect]` must give a `reason`.
- Formatting is enforced, never hand-tuned:
  - Rust: `cargo +nightly fmt` (`rustfmt.toml`; import grouping, import merging and impl item ordering are nightly-only options, so formatting uses nightly while building uses the pinned stable toolchain). `OPENWOOT_NIGHTLY` names the nightly `xtask` uses instead of `nightly`; CI sets it to the dated nightly it installs.
  - TOML: `taplo fmt` (`taplo.toml`); `Cargo.toml` dependency and section order: `cargo sort --workspace`.
- Before every commit: `cargo xtask check` and `cargo test --workspace`.
- Modules use the 2018+ file layout: a module `keys` with children is `src/keys.rs` plus `src/keys/actuation.rs`; no `mod.rs` anywhere (clippy `mod_module_files` is denied).
- Every crate and every module with children is a facade: child modules are private (`mod actuation;`), and the parent re-exports the public API (`pub use actuation::{ActuationPoint, Actuation};`). Callers write `openwoot::keys::ActuationPoint`, never `openwoot::keys::actuation::ActuationPoint`. Items shared only inside the crate are `pub(crate)`; `unreachable_pub` warns about anything public that the facade does not export.
- Small modules named for what they hold, one concept per file; public items first, private helpers after.

## Tests

Follows the Rust Book (ch. 11.3) for unit tests and matklad's "Delete Cargo Integration Tests" for integration tests:

- Unit tests live in the file they test, in `#[cfg(test)] mod tests { use super::*; ... }` at the end of the file.
- Integration tests: one integration test crate per package, `tests/it/main.rs`, declaring one module per behaviour area (`tests/it/keys.rs`, `tests/it/flash.rs`) and shared setup as a plain module (`tests/it/support.rs`). One binary links faster than one per file, and no `mod.rs` is needed.
- Test names state the behaviour (`rapid_trigger_releases_after_upstroke`). No test-only code outside test modules and `tests/`.
