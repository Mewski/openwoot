# Storage

What the firmware keeps across a power cycle, where it lies, how it is written and what survives a power cut. The code is `openwoot::storage` (`crates/openwoot/src/storage/`), the flash driver `openwoot_drivers::spi_nor::SpiNor`, the bus `hal::spi` of each chip HAL, and the board facts `boards/<board>/src/storage.rs`.

## Where data lives

Both boards carry an 8 MiB SPI NOR flash (W25Q64 or GD25Q64 class, 4096-byte sectors, 256-byte pages).

| Medium | Wooting 80HE | Wooting 60HE+ |
| --- | --- | --- |
| settings partition | NOR sectors 0 to 127 (`0x00_0000`-`0x07_ffff`, 512 KiB) | the same |
| unused, never touched | NOR sectors 128 to 2046 | NOR sectors 128 to 2047 |
| factory device-information record | NOR sector 2047 (`0x7f_f000`), read only | microcontroller flash page `0x080f_f000`, read only |
| physical layout | field of the device-information record, unless the settings store holds a layout (`storage::LayoutOverride`) | bit 0 of the user option byte (`FMC_OBSTAT` bits 17..10), with the same exception |
| serial text for the factory bootloader | microcontroller flash page `0x080f_e000`, read for the USB serial string, never written | page `0x080f_d000`, read, never written |

`NorLayout` (in `boards/<board>/src/storage.rs`) states the chip size, the settings partition and the device-information sector. `NorLayout::settings_region` is evaluated in a constant and fails the build unless the partition is whole sectors, at least two and at most 128 (the store's page cache), inside the chip and apart from the device-information sector. `Partition` receives only that region and refuses every read, program or erase outside it, so the settings store cannot reach the device-information sector even through a bug in the store.

## Bus and driver

`hal::spi::Spi` is the SPI master: mode 0, 8 bit, most significant bit first, software chip select, clock = bus clock / 2 (80HE: `SPI0` at 50 MHz on PB3, PA7, PB4; 60HE+: `SPI1` at 30 MHz on PB13, PB15, PB14). Every transfer runs by DMA in both directions; the receive channel's interrupt (priority 1) wakes the waiting task, and the completion is also visible in the DMA flags, so the same code works under `embassy_futures::block_on`, which the settings store uses for every access (in thread mode only, where the interrupt executors pre-empt it). Dropping a transfer aborts it. Bytes sent while reading are `0x00`.

| Board | Receive | Transmit | Interrupt |
| --- | --- | --- | --- |
| Wooting 80HE | `DMA1` channel 2, sub-peripheral 3 | `DMA1` channel 3, sub-peripheral 3 | `DMA1_Channel2` |
| Wooting 60HE+ | `DMA0` channel 3 | `DMA0` channel 4 | `DMA0_Channel3` |

`hal::spi::Device` adds the chip-select pin (PD2 on the 80HE, PB12 on the 60HE+): low for one `embedded_hal_async::spi::SpiDevice` transaction, high again afterwards, also when the transaction is dropped.

`SpiNor` implements `embedded_storage_async::nor_flash::NorFlash` (read size 1, write size 4, erase size 4096) and `MultiwriteNorFlash` with these commands:

| Command | Use |
| --- | --- |
| `0x05` read status | before every command until bit 0 (busy) is clear, and after every page program and sector erase, so a finished future means a finished flash operation; the task yields between polls. A chip that stays busy fails the command with `NotReady` after 100 000 polls and 20 000 more polls 100 µs apart (at least 2 s); from then on each command polls once until the chip reports ready again |
| `0x06` write enable | before every page program and sector erase; unless the status then shows bit 1 (write enabled) the command fails with `WriteRefused` |
| `0x0b` fast read | 24-bit address, one dummy byte `0xff` |
| `0x02` page program | split at 256-byte page boundaries |
| `0x20` sector erase | one 4096-byte sector |
| `0x90` manufacturer and device id | address 0, two bytes |
| `0x4b` unique id | address 0, four dummy bytes `0xff`, eight bytes (so the answer equals stock's) |

## Settings store

The settings are a `sequential-storage` 8.0.2 map (`storage::Settings`) on the partition, with all three caches (page states and pointers for 128 sectors, pointers for 256 keys).

- Key: 16 bits, the slot in the high byte (`Scope::Profile(n)` = `n`, `Scope::Linked(n)` = `0x80 | n`, `Scope::Global` = `0xff`) and the item in the low byte (`RecordKey::new`, `RecordKey::of::<R>`). Items are unique within each scope; a profile slot is always below the profile capacity and a linked slot below `profile::MAX_LINKED` (10), so neither reaches `0xff`.
- Linked profiles: a linked profile's parts lie under `Scope::Linked(n)` with the item numbers of an onboard profile's, and its app links under items `0x30..0x3f` (`apps::Link`, version 1, one record per link, gap-free from `0x30`; deleting one moves the later ones down and removes the last). Global item `0x19` (`profile::LinkedCount`) holds the number of linked profiles; reorders do not touch linked profiles, and creating one removes whatever an earlier one of that slot left behind. The stored active profile is always onboard: while a linked profile is active, the onboard profile it returns to is stored instead.
- Macros: the keyboard-wide macro library, shared by every profile, lies under `Scope::Global` at items `0x20..0x3f`, macro slot `n` at item `0x20 + n` (`macros::Macro`, version 1, the macro in the postcard format, at most 2000 bytes, `macros::MAX_ENCODED_LEN`); `SetMacro` stores a slot at once unless it already holds the same bytes, `ClearMacro` removes it, `Revert` keeps them and `FactoryReset` erases them with the rest of the store. A record that does not decode reads as an empty slot. When a key triggers a macro, the `profiles` task loads the record and copies its steps into the playback buffer of the key task (`profile::Model::load_macro`, see [protocol](protocol.md#configuration-model)).
- Profile order: a profile's records lie under its storage slot, which global item `0x17` (`profile::Order`, the storage slot of each profile slot, a permutation of the profile capacity of at most 16 slots) gives; without a stored order, or with one that is not such a permutation, every profile slot is its own storage slot. `SwapProfiles` and `MoveProfile` store only this record, so a reorder never moves a profile's records. The active profile (global item `0x10`, `keys::ActiveProfile`) is stored as its storage slot, only when it differs from the stored one (`ActivateProfile` at once, a switch by key two seconds after the last one), since every stored version stays in the store until its sector is collected and `Settings::open` walks them all. A part a profile has not stored is the factory part of its storage slot, except the keymaps: a profile without a keymaps record (profile item `0x11`) uses the keymaps of the profile in slot 0 (keymap links, see [protocol](protocol.md#configuration-model)), so re-linking a profile removes its record. The device name is global item `0x18` (`profile::DeviceName`).
- Value: the record version (one byte) followed by the record in the postcard format, written and read with `openwoot_protocol::wire` (the bytes postcard 1.2 writes; a decode ignores bytes behind the record, as `postcard::from_bytes` does, so records stored by earlier, postcard-based firmware load unchanged). A record type implements `storage::Record` (`wire::Encode` and `wire::Decode`, derived) with its `ITEM` and `VERSION`; the body holds at most 2048 bytes (the buffer is rounded up to whole 4-byte words, so a body of that size also reads back), and a longer body stores nothing.
- Versions: a record whose version differs from its type's `VERSION`, or one that does not decode, counts as absent and the caller uses its default (the profile information, `profile::Info`, is version 2 since it holds an icon, so a version-1 record reads as the factory name and colour; the light-bar records, profile item `0x24` and global item `0x14`, are version 2 since their entries carry a title; the gamepad settings, profile item `0x15`, are version 2 since the stick bias keeps its percentage while it is off). `profile::Model` also validates every part it loads with `configuration::Validate`, as for a `Set*` request, against the board's key matrix and profile capacity (light-bar ranges only against 255 LEDs, since the model does not know the board's light bar), and uses the factory part of its storage slot for a part that fails; keymaps and colour maps fall back layer by layer. The switch settings (global item `0x15`, `switches::Settings` in postcard: the default, then one optional switch per key of the matrix) must also pass the firmware's model table (known model, offset below its travel, at most 30 tuned pairs); a record that fails loads as the factory switches.
- Lookups: `Settings::open` walks the stored items once, reads the format record on the way, and keeps the set of stored keys: a bitset over the scopes (profile slots 0 to 15, linked profiles 0 to 9, global) and the items 0 to 63, 216 bytes. A key outside it (the firmware writes none) leaves the set incomplete, and then every lookup reads the flash until the next walk. `Settings::load`, `Settings::load_stored` and `Settings::remove` answer a key that is not stored without reading the flash; every store and remove updates the set. A stored key is found through the store's key cache. `Settings::visit` walks every stored item once (several items per key may appear; the last one is current).
- Read-ahead: `Partition` keeps a 256-byte window of the flash in RAM (272 bytes with its bookkeeping). A read the window holds is served from it; any other read of at most 256 bytes refills the window from the start of the read (whole read units, cut at the end of the partition, so it never reaches another region of the chip) and is served from it; a longer read goes to the flash directly. A read that repeats the previous read exactly (sequential-storage reads a header or body again after a checksum mismatch) refills the window from the flash, so that retry still reaches the flash. Every program and erase drops the window, and a new `Partition` starts without one. A walk over the items (opening the store, the lookup of a key outside the key cache, a remove, `Settings::visit`, `Settings::usage`) therefore costs about one flash read per 256 bytes stored instead of two reads per item (header, then body), so superseded versions no longer slow the start-up down by their number: opening a sixteen-sector store that holds six profile records and a one-byte record stored 2440 times (once per profile switch, as found on an 80HE) reads the flash about 150 times instead of about 4 900 (`crates/openwoot/tests/it/storage/read_ahead.rs` holds it below 400).
- Usage: `Settings::usage` walks the items once, renews the set of stored keys on the way and returns `diagnostics::StorageUsage` (`GetStorageUsage`): `capacity` (bytes of the partition), `used` (bytes of every stored item, current and superseded: the item header, `MapStorage::item_overhead_size`, 8 bytes, plus the data, the 2-byte key, the version byte and the body, rounded up to whole 4-byte flash words), `records` (the keys in the set of stored keys, one per current record) and `items` (stored items, current and superseded). Items marked removed and the sector markers are not counted. A superseded item leaves once garbage collection erases its sector: the store keeps one sector empty, and when the sector in use is full it moves the current records out of the oldest sector and erases it.
- `Settings::store`, `Settings::remove` (marks the item erased; scans the used area) and `Settings::factory_reset` (marks the format record erased, erases the partition, then writes a new format record).
- In place, for records too large to pass around on the stack: `Settings::load_stored(key)` returns the stored version and body undecoded, and `Settings::store_with(key, version, encode)` takes `encode` as a `&dyn Fn` that writes the body straight into the store's buffer (`None` or a length beyond the buffer stores nothing). The store's API is synchronous: each kind of access (load, store, remove, walk, erase) has one path that runs the flash future to completion with `embassy_futures::block_on`, and typed decoding and encoding run around it. `profile::Model` decodes its parts this way one keymap or colour layer at a time (`wire::take`), and encodes the key parts and the colour maps entry by entry from the shared state of the running profile into one `wire::Writer`, so no critical section encodes a whole record, and none is held across flash I/O.
- Placement: the store (2 KB buffer, the page and key cache, the set of stored keys and the partition's read-ahead) is never moved. A board initialises `Settings::new()` in a static cell (`storage::SETTINGS_STORE`) at start-up, so the store lies in `.bss` rather than `.data`; `Settings::open` fills it in place, and `storage::Storage` and `profile::Model` hold `&mut Settings`.

Global item 0 is the format record (`Format { generation: 1 }`). `Settings::open` formats the partition when the record is missing or different, or when the store cannot be read (first boot, the stock littlefs volume, a future incompatible store, corrupted content), and reports `Opened::Formatted(FormatReason::Unrecognised)`; a format request of the factory bootloader (`0x420` in backup register 1, taken by `Bootloader::take_format_request`) formats it too (`FormatReason::Requested`). Formatting first marks the old format record erased, so an interrupted format or factory reset never leaves part of the old settings behind a valid format record: the next start formats again. A read error of the flash changes nothing and leaves the keyboard without a store: `Storage::settings` is `None` and `Storage::opened` holds the error, every part loads as its factory part, every store answers `StorageInaccessible`, and the board counts the failed open as one failed storage access in the diagnostics.

Switching from stock to this firmware therefore replaces the stock littlefs volume in sectors 0 to 127 with this store; the device-information sector is untouched. Switching back, the stock firmware finds no littlefs volume, formats the chip and starts with factory settings.

## Device information

The factory record is read once at start-up through a `storage::DeviceInfoSource` (`storage::NorSector` on the 80HE, `storage::McuPage` on the 60HE+) into `storage::DeviceInfo`: the serial number (`SerialNumber`, printed by `SerialNumber::text` as `A<supplier>B<year><week>W<product>[T<pcb design>]<revision>[<minor revision>][S<edition>]<stage letter><product id>`, the public Wooting format with stock's field widths: the supplier, product and revision print their low byte, and a two-digit field above 99 prints three digits that `SerialNumber::parse` does not read back), the auxiliary record (`AuxRecord`, at most 58 bytes, kept as bytes), the physical layout and the lock mode (kept as its number).

| Marker at `+0xffc` | Length prefix | Largest payload |
| --- | --- | --- |
| `0x1337` | 1 byte | 254 bytes |
| `0x1338` | 2 bytes, little endian | 4090 bytes |
| none, first 30 bytes `0xff` | | blank |
| none, otherwise | 80HE: 1 byte (`Unmarked::ShortFormat`); 60HE+: the older raw record (`Unmarked::RawRecord`) | |

The payload is the protobuf message `DeviceInfo` of the stock schema (field 1 serial number with required fields 1 to 7, 2 auxiliary record, 3 physical layout, 4 lock mode). For the serial number and the physical layout, a missing required field, a wrong wire type or a value wider than its field makes the record undecodable; an auxiliary record or lock mode that does not decode (longer than 58 bytes, without its field 1, not clean protobuf, a wrong wire type, a lock mode above 255) is left out and the rest of the record is kept. A varint longer than ten bytes or wider than 64 bits is malformed. The raw record of the 60HE+ is the serial number without its optional fields, a length byte at offset 12 and an encoded auxiliary record at offset 13 (left out when it does not decode). A length beyond the 44 bytes of the raw record means "no auxiliary record"; the bytes behind the record are never decoded.

The firmware never writes the device information on either board. Deviation from stock on the 80HE: host commands that change the serial number, the auxiliary record, the layout or the lock mode cannot store them there. A layout chosen with `SetLayout` lives in the settings store instead (global item `0x16`, `storage::LayoutOverride(variant)`, the variant being the layout's position in `Capabilities::layouts`); the factory record stays as it is.

The physical layout is a `storage::LayoutVariantSource`: `InDeviceInfo` (80HE: the record's field, 0 when absent) or `OptionBit` (60HE+: bit 0 of the user option byte, read by `hal::flash::user_option`); `Storage::open` keeps it as `Storage::factory_layout_variant`. Once the settings store is open, `Storage::open` replaces it with a stored `LayoutOverride` below `configuration::LAYOUTS` (3; a larger stored variant counts as absent) in `Storage::layout_variant`, so the sensor map, keymap, LED map, `GetLayout`'s `active` layout and the stock layout byte all follow it; `FactoryReset` erases it with the rest of the store. The board hands the factory variant to the model (`profile::Model::with_factory_variant`), which reports as `GetLayout`'s `chosen` layout the one a `SetLayout` chose, otherwise the stored `LayoutOverride`, otherwise the factory variant.

## Identification

Start-up (`storage::Storage::open` with the board's `SETTINGS`, `DEVICE_INFO` and `LAYOUT_VARIANT` from `boards/<board>/src/storage.rs`) also reads the flash ids (`SpiNor::identification`, `SpiNor::unique_id`, into `storage::NorIdentity`, absent when the chip does not answer or stays busy; a chip whose data line is held low reads as zero ids, which the responder reports the same way as absent ids), and the board reads the 96-bit unique id of the microcontroller (`hal::flash::unique_id`: `0x1fff_7a10` on the GD32F425, `0x1fff_f7e8` on the GD32F303). The stock identification responder (`protocol::StockIdentity`) answers them for feature command 3 selectors 1 and 3 (the flash ids as manufacturer, device and unique id, zero when absent), and the physical layout as byte 5 of the device settings (command 19).

## Power loss

The host tests (`crates/openwoot/tests/it/storage/`) run the store on a NOR model that cuts the power at every program word and every eighth of a sector erase: a cut word is half programmed, a cut erase leaves the sector erased from its start up to the cut. For 150 fill levels of a four-sector partition, a cut at every step of the next store keeps every other setting, leaves the stored key at its old or its new value and opens the store again without formatting. A cut at any step of a remove keeps every other setting; a cut at any step of a factory reset of a sixteen-sector store with 60 live records leaves all of them or none and a working store; a cut while foreign content is formatted leaves a working store. In `crates/openwoot/tests/it/profile.rs`, a cut at any step of a profile deletion leaves the profile whole or gone. Wear over 3000 stores spreads within one erase per sector, a partition that starts behind other sectors leaves them untouched, and the device-information sector is never erased. `crates/openwoot/tests/it/storage/opening.rs` starts the storage on a flash bus that fails and on a flash that always reads busy: both finish without a store. All of these run through the read-ahead: the program or erase a cut interrupts has dropped the window already, and every start after a cut opens a new `Partition`.

Not covered: a NOR part that leaves an interrupted erase with random or zero content can lose unrelated settings during the repair after the next start (sequential-storage issue 149, mitigation not released for 8.0.2). The consequence is settings falling back to defaults, never a brick or a lost device-information record.
